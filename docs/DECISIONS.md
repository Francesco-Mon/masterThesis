# DECISIONS

One short paragraph per decision: what, why, alternatives dropped. Newest last.

- 2026-11-02 - Emulated environment instead of Orion-LD for the first iteration (time: 1 month); same entity names as thesis Ch.5, so the broker can be swapped in later. Dropped: Orion-LD container (only if time remains).
- 2026-11-02 - Intent Grounding is the component studied in depth; candidate A (LLM via OpenRouter, structured output) is the primary candidate, C (embeddings) the secondary one. Dropped: fine-tuned encoder / GRU (only if time remains).
- 2026-11-02 - Ledger anchoring not implemented in the first iteration; event log with commitments + hash chain + verifier is. Thesis presents the ledger as designed.
- 2026-11-02 - Development entirely local, in VS Code (cloud development environments dropped to reduce complexity). OpenRouter key in a git-ignored `.env`.
- 2026-11-02 - Python 3.12 in a local `.venv` (macOS system `python` is 3.9; 3.12 is invoked as `python3.12`). Packaging with setuptools + `pyproject.toml`, `src/` layout, editable install. Heavy dependencies split into extras (`llm`, `embeddings`, `ui`) installed only when the component that needs them is built; core = pydantic, python-dotenv, pyyaml. Live tests marked `live` and excluded by default via pytest `addopts`. Dropped: uv/poetry (one more tool to learn, no benefit here).
- 2026-11-02 - The virtual environment is kept outside any synchronized folder, with a `.venv` symlink in the repo. A file-sync service can set the macOS `hidden` flag on files under `.venv`, and Python 3.12 skips hidden `.pth` files, so the editable install silently breaks; a synchronized venv would also upload GBs of dependencies. pytest additionally sets `pythonpath = ["src"]`, so tests never depend on the install. Dropped: a sync-exclusion naming trick for the folder (less obvious), removing the flag by hand (the sync service puts it back).
- 2026-11-02 - Contracts, deviations from / refinements of docs/CONTRACTS.md:
  (a) All contract models reject unknown fields (`extra="forbid"`) and are immutable (`frozen`); times must be timezone-aware and are normalised to UTC (serialised with `Z`).
  (b) `action` closed enum = activate, deactivate, increase, decrease, set, query (the list proposed in CONTRACTS.md, no extra verbs). `controlledProperty` stays a string; its membership in the catalogue is checked through Pydantic validation context (`context={"catalogue_properties": ...}`), because the contract alone does not know the building.
  (c) `reason` is a closed enum, so it can be counted in the evaluation: clarification = ambiguous_target, ambiguous_action, missing_information, low_confidence, invalid_output (output still invalid after bounded retry); unsupported = capability_absent, command_absent, out_of_scope (incl. injection-like requests). CONTRACTS.md only gave examples.
  (d) R7 `history` = list of previous user utterances (strings, oldest first); `language` = two-letter ISO 639-1 code.
  (e) C3: one call model per operation, so arguments are checked against the operation (e.g. `listDevices` needs `zoneId`, `listZones` takes none). `ToolResult.error` is a closed enum (operation_not_allowed, invalid_args, unknown_zone, unknown_device, command_not_supported, out_of_scope, device_failure); `ok` and `error` are mutually exclusive; `operation` is null only for a rejected call whose operation is not one of the four. `state` holds the observation of any operation (zone list, device list or device state).
  (f) C4: `guard` (T1..T12) must match `from`/`to` according to the transition table, which lives in `contracts/event.py` (`TRANSITIONS`) and will be reused by the engine. `outcome` = ToolResult, or a string reason for recovery. Stored form: `salt`, `commitment`, `link` are 64-char lowercase hex; after erasure `record` and `salt` are both null, never one alone. The position `i` used in the hash is the line position in the store (not repeated in the stored form, as in SPEC section 7).
  (g) ActionPlan: `steps` may be empty (= "no applicable step", which the engine maps to T5 Plan -> Recover); step guard is a discriminated union on `type` (`now` | `on_enter_zone` with `zoneId`).
- 2026-11-02 - The repository itself is also kept outside any synchronized folder; the virtual environment stays outside the repo with the `.venv` symlink (the workaround above is then no longer needed but is harmless).
- 2026-11-02 - Scenario (`data/scenario.yaml`): 8 zones (lobby, hallway, corridor, office, meeting_room, kitchen, storage, server_room), 3 device categories with controlledProperty light / shading / temperature. Built to make grounding non-trivial: similar adjacent names hallway/corridor; storage (no device) and server_room (no lamp); lamp_corridor and lamp_kitchen without `dim`, blind_meeting_room without `setPosition`; `absentCapabilities` (sound, ventilation, humidity, lightColor) offered by no device, used by tests and the evaluation set. server_room is outside the Person Agent's scope, to exercise `out_of_scope`. Short ids (`lamp_hallway`) instead of NGSI-LD URNs, mapped later if Orion-LD is added.
- 2026-11-02 - Emulated environment: Pydantic entities with the thesis names (`Building`, `Zone`, `Device`, `PositioningSignal`, camelCase fields); the loader checks references (symmetric adjacency, known refZone, commands defined for the category, paths through adjacent zones). Command semantics live in one table per category (`environment/commands.py`); a device's `supportedCommand` is a subset. Device state: lamp `power`+`brightness`, blind `position` (0 closed..100 open), thermostat `setpoint` (16-28 C). The emulator has a test hook `inject_failure(device, times)` so the engine tests can reach T10/T11. Authentication is an emulated token issued to agent ids registered in the scenario (no secret). Dropped: one Python class per device category (more code, no benefit for the thesis).
- 2026-11-02 - Mobility simulator: one BLE beacon per zone; the phone hears its own zone's beacon at -55 dBm, adjacent zones at -80 dBm, non-adjacent zones not at all; walking A -> B crosses the two levels linearly over `transitTicks`; a `doorway` segment holds both at the midpoint (the case that makes a naive estimator oscillate). Gaussian noise (sigma 3 dB, `random.Random(seed)`), 1 tick = 1 s of simulated time from a fixed start, so runs are reproducible. Each tick also carries the ground-truth zone (tests/evaluation only). Signals go out one by one through a callback (`run(deliver)`); in the wired system `deliver` is `EmulatedEnvironment.publish`, which pushes them to subscriptions filtered by `refSubject`. Dropped: 2-D coordinates and a path-loss model (zone-level localization is all the thesis needs).
- 2026-11-02 - Localization: proximity = strongest beacon after exponential smoothing (alpha 0.5); the decision runs once per scan (readings with the same `observedAt`), so the arrival order inside a scan does not matter (deciding per reading made the first weak adjacent beacon win the initial estimate). Hysteresis based on adjacency: move to an adjacent zone only if it beats the current one by >= 8 dB; never move to a non-adjacent zone while the current beacon is still heard (stale after 3 s = track lost). Margin 8 dB chosen by a sweep over 200 seeds (alpha 0.3-0.5 x margin 6/8/10): 200/200 correct sequences on both scripted paths, zone change at most 3 s after the true one; 6 dB still oscillated on the doorway for 10/200 seeds. `confidence` = logistic(margin over the strongest other beacon / 5 dB): about 0.5 on a doorway, > 0.9 inside a zone, < 0.5 while hysteresis holds the old zone, so the engine's theta (0.6) sends doorway cases to Recover. R5 = `estimate()`, R6 = `subscribe(listener)` with `ZoneChangedEvent` (C1). Dropped: fingerprinting / trilateration (zone level is enough), a time-based dwell counter (the margin alone was sufficient).
- 2026-11-02 - Environment Binding: `EnvironmentBinding(brokers).bind(endpoint, agent_id, subject)` runs the five protocol steps in order and returns a `BoundSession` (session id, endpoint, token, spatial model, scope, catalogue, subscription); each failing step raises `BindingError` naming the step. Locate resolves the endpoint through a dict endpoint -> emulated broker (stands for the network). The catalogue is the C2 `ZoneCatalogue` list, built only by reading each device's `supportedCommand`, and covers only the zones in the agent's scope (zones without devices are kept, with an empty list, so grounding can tell "no lamp here"); the spatial model keeps every zone, because the user can walk anywhere. Subscribe creates the broker subscription at bind time and exposes `add_listener`, so Localization can be built afterwards from the spatial model (it needs the adjacency) and then attached. R13 is realised as this subscription: positioning is a push channel set up by Binding, not one of the four operations of the Environment Interface. The session object is injected into the Environment Interface (R11). The catalogue is a snapshot at bind time (re-binding refreshes it). Dropped: periodic catalogue refresh, real token expiry.
- 2026-11-02 - Environment Interface: a single entry point `execute(call)` accepting a C3 model or raw JSON-like data (what a planner or LLM would produce); thin wrappers (`list_zones`, ...) go through the same path. Checks in fixed order: allow-list (`ALLOWED_OPERATIONS`, the four operations, in code) -> arguments valid for the operation -> zone/device known -> in the scope negotiated at binding -> command in the device's live `supportedCommand` -> value valid. Every rejection is a `ToolResult(ok=False, error=...)` and never reaches the emulator; only `invokeCommand` calls the emulator's `execute` (tested by comparing full state snapshots). Out-of-scope devices are distinguished from unknown ones (`out_of_scope` vs `unknown_device`), so the evaluation can count hallucinated ids separately from scope violations. Using a closed session raises `RuntimeError` (programming error, not a tool outcome). Added `python -m cpsagent.demo` (CLI demo of binding, capability catalogue, localization and Environment Interface). Dropped: per-operation Python methods as the primary API (one entry point is easier to log from the engine).
- 2026-11-02 - Orchestration Engine in plain Python, no LangGraph: the machine has six states and twelve rows, and the thesis needs the table to be inspectable and identical to Table 5.3; a graph framework would add a dependency and hide the guards inside its routing. The table is data (`engine/transitions.py`): rows (id, from, trigger, guard wording, condition, to), with from/to read from `contracts.TRANSITIONS`; a condition is a pure function of a `Context` snapshot (confidences, step count, retries, pending step, zone changed, following, intent ended). `select(state, trigger, ctx)` returns the single row that fires; guards are mutually exclusive by construction (tested on a grid of contexts). The engine only runs the activity of each state and asks the table. Parameters in `EngineConfig` (theta 0.6, STEP_LIMIT 8, RETRY_LIMIT 2). Dropped: LangGraph (no benefit at this size), if/else per state (the table would not be visible in the code).
- 2026-11-02 - Engine semantics where Table 5.3 is silent:
  (a) Interpret: T2 needs both the ZoneEstimate and the StructuredIntent confidence >= theta. If the zone is below theta (or missing) the grounder is not called (no cost spent on an unreliable zone). Clarification, unsupported, an intent whose property is not in the catalogue (re-checked by the engine, never trusted) and low intent confidence all go T3 -> Recover, with the reason in `outcome` (`zone_confidence_low`, `intent_confidence_low`, `clarification:<reason>`, `unsupported:<reason>`).
  (b) Plan -> Act (T4) needs a step applicable *now* (guard `now`, or `on_enter_zone` of the current zone); otherwise T5 with `capability_absent` (no device offers the property where needed) or `command_absent` (one does, without the command).
  (c) STEP_LIMIT = max commands per request, retries included; it is checked *before* sending (T7 sends nothing), so at most STEP_LIMIT commands reach the environment. RETRY_LIMIT = retries per step (limit 2 = 3 attempts). Any failed ToolResult is retried (in practice only `device_failure` happens, the planner reads the catalogue).
  (d) A `following` intent keeps the engine waiting in Observe after its steps (no row fires: nothing pending, zone unchanged); a zone_changed event (R6) arriving there makes `validFor` stale -> T9 -> Plan with the same intent (no re-grounding). It ends with T8 when a new request arrives (`superseded_by_request`) or the session is closed (`session_closed`). Zone changes in any other state are ignored. Because STEP_LIMIT counts per request, a following intent also ends (T7) after STEP_LIMIT commands: this is the bound that makes the Observe -> Plan -> Act loop finite.
  (e) **Gap in Table 5.3**: after a successful command, if the plan has another step applicable now (e.g. scope `environment`: six lamps), no row leads back to Act (T10 is for failures). The prototype treats this as `validFor` stale: T9 -> Plan, with `outcome="steps_pending"` (vs `zone_changed`), so each command still gets its own Act -> Observe record and nothing is re-grounded; steps already done in the current zone are not re-planned. **Proposal for the thesis**: either state that T9 also covers "steps pending", or add a row `Observe | Outcome received | step pending | Act`.
  (f) Recover applies one fallback and always goes to Perceive (T12): the grounder's clarification question, "which room are you in?" for a low zone confidence, otherwise a message with the reason; the outcome of T12 is `clarification_asked` or `user_informed`. Replies (R3) are returned by `handle_request` and pushed to an optional `notify` callback (zone-driven activity has no caller to return to).
- 2026-11-02 - Rule-based planner, no LLM in Plan: once the intent is grounded, intent + zone + catalogue + adjacency determine the plan, so an LLM would add cost and nondeterminism without changing the result (an LLM planner is left for later, only if time remains). `scope` -> target zones: current_zone = here, now; path = here now + every adjacent zone except `previousZoneId` (direction of travel) with `on_enter_zone`; environment = every catalogued zone, now. Command from a (category, action) rule table, kept only if the device's `supportedCommand` lists it. StructuredIntent has no value slot, so `decrease light` = dim 30, thermostat increase/decrease = 23/19 C, and `set`/`query` are not planned (T5). Known limit: walking a `following` intent into a zone without the device (storage) ends it via T5.
- 2026-11-02 - `FakeGrounder`: script text -> R8 result (matching ignores case and spaces), a default for unscripted text (clarification `missing_information` if none), and `calls` recording every R7 request so tests can prove the intent is computed once per request.
- 2026-11-02 - Event log, encoding fixed for the thesis: SHA-256 over raw bytes; `c_i = H(salt || enc(r_i))` with a 32-byte salt from `secrets`; `h_i = H(h_{i-1} || c_i || i)` with `i` as 8-byte big-endian; `h_0 = H(session id UTF-8)`; `enc` = `json.dumps(sort_keys, separators=(",",":"), ensure_ascii=False)` UTF-8 of the record's JSON form (camelCase, times as `...Z`). The commitment is computed and verified on the record *as stored* (raw JSON), never on a re-serialised Pydantic model, so a serialisation change cannot break old logs. Not full RFC 8785 (JCS): Python's float repr is already shortest-round-trip, enough for one implementation. Dropped: JCS library (one more dependency for a case we do not have).
- 2026-11-02 - Event store and verifier: JSONL, one StoredRecord per line, position `i` = line number. Append-only except erasure, which nulls `record`+`salt` of one line and rewrites the file atomically (temp file + `os.replace`); erasing twice is a no-op. The verifier recomputes `c_i` (kept records) and `h_i` (all lines), checks `seq == i` and the session, continues from the stored link so each error is reported at its position, and lists erased positions separately (not an error). Known limit, stated in the thesis: truncation of the tail and a full rewrite with recomputed links verify locally; they fail only against a head kept elsewhere (`expected_head`), which is what ledger anchoring (R17) would provide - tested to show exactly this.
- 2026-11-02 - Asynchronous recording: `EventLog.submit(fields)` only enqueues (`queue.Queue`); one background thread assigns `seq`, validates the C4 EventRecord, salts, hashes and appends; `close()`/`with` flushes and joins. A thread rather than asyncio because the engine is synchronous; FIFO order of the queue keeps `seq` equal to transition order. A record that fails validation (a bug) is kept in `errors` and not written, so the chain stays gap-free; tests assert `errors` is empty. Reopening a store continues its chain from the last link.
- 2026-11-02 - Engine-log integration: the engine's `recorder` is wired to `EventLog.submit(transition.record_fields())`; the engine adds nothing else (no hashing, no I/O on its path). `seq` and `session` are added by the log. Record content per row: `zone` = ZoneEstimate in force (null at T1, before R5), `intent` from T2 until the intent ends, `action` = the call planned (T4) or invoked (T6, T10, T11), `outcome` = ToolResult (T6, T8, T10) or a reason string (T3, T5, T7, T9 `zone_changed`/`steps_pending`, T11, T12, T8 `superseded_by_request`/`session_closed`). Demo `python -m cpsagent.demo_agent`: real ZoneEstimator on the scripted walk, request issued when Localization first places the user in the hallway with confidence >= theta, record times = simulated time; the log goes to `logs/` (git-ignored: random salts change at every run).
- 2026-11-02 - OpenRouter client (`grounding/openrouter.py`): OpenAI SDK with OpenRouter's base URL; the key comes from the environment / `.env` (python-dotenv) and is passed only to the SDK (tested: it never reaches the call log or the cache). One method `chat(messages, schema, temperature, attempt)` always requests `response_format: json_schema` (strict) and `usage: {include: true}`, so the cost is OpenRouter's `usage.cost`, never estimated. Cache: one JSON file per call in `.llm_cache/`, key = SHA-256 of (model, messages, schema, temperature); errors and empty answers are not cached. Call log: one line per call in `results/llm_calls.jsonl` (time, runId, requested/returned model, temperature, attempt, status, tokens, `costUsd`, `spentUsd`, latency, `cacheHit`); on a cache hit tokens/cost/latency are those of the original call, so a rerun reproduces the measurements, while `spentUsd` = 0 is the real spend. Rate limiter: sliding 60 s window, `LLM_RPM` (default 20 = free tier), used only for real calls. Spending cap `MAX_COST_USD` (default 0.5) per client instance (= per run): checked before each real call, so a run can exceed it by at most one call; cached answers are still served after the cap. 401/403 raise `AuthError` (reported, not retried); other API failures raise `LLMCallError` after the SDK's own backoff (2 HTTP retries on 429/5xx, inside one logged call). The 50-requests/day free quota is not tracked client-side: the cache makes reruns free and a 429 surfaces as `LLMCallError`. Dropped: litellm / an OpenRouter-specific SDK (one more dependency, the OpenAI SDK is enough).
- 2026-11-02 - Grounder A (`grounding/llm.py`): (a) **Wire schema**: the model gets a flat object (kind, action, controlledProperty, scope, persistence, confidence, question, reason; all required, unused ones null, `additionalProperties: false`) generated from the C2 enums, not the Pydantic schema of the discriminated union: strict structured output across providers accepts only a subset of JSON Schema (no `oneOf`/`$defs`, every field required). The answer is mapped back to the C2 `GroundingResult` and validated by Pydantic, so C2 stays the single source of truth; unknown keys are an error (retried). `controlledProperty` is a free string in the schema (not an enum of the catalogue): the catalogue check is done in code via the validation context, and it lets the evaluation count off-catalogue proposals (Security). (b) **Prompt**: fixed system rules + one user message that is a JSON document; the user's text and history are JSON string values (cannot close a delimiter), the system message never contains user text, and the rules say they are data and that injection-like or non-environment requests are `unsupported/out_of_scope`. No few-shot examples, to avoid leaking evaluation items into the prompt. Zone confidence and `observedAt` are not sent (the engine already gated on confidence; the timestamp would defeat the cache). (c) **Checks in code before the LLM**: the user's zone must be a catalogued zone (in scope), otherwise `unsupported/out_of_scope` with no call. (d) **Bounded retry**: max 2 retries (3 calls), each with the previous answer and the validation error appended; when exhausted, `unsupported/capability_absent` if the last error was an off-catalogue property, else `clarification/invalid_output`. (e) **New reason** `clarification/service_unavailable` (network, 5xx, 429 after the SDK backoff), so provider failures are not counted as wrong groundings; `AuthError`, `BudgetExceededError` and a missing key propagate and stop the run. (f) `last_trace` keeps the attempts (raw answer + error), cost, latency and cache hits of the last call, for the evaluation. (g) Gap in C2: StructuredIntent had no target zone, so "turn on the lamp in the corridor" said in the hallway could not be expressed; resolved by `targetZoneId` (below). The candidate is imported from `cpsagent.grounding.llm`, not re-exported by `cpsagent.grounding`, so the core does not need the `llm` extra.
- 2026-11-02 - `targetZoneId` in StructuredIntent: optional, present only when the user names a zone other than the current one. It *replaces* the current zone, so it is allowed only with `scope: current_zone` (model validator; path/environment + a named zone has no clear meaning). It must be a catalogued zone, i.e. in the agent's scope: checked by a validator with context `catalogue_zones` (like `controlledProperty`), by Grounder A after validation, and again by the engine (never trusted: `unsupported:out_of_scope` at T3). Grounder A: a target outside the catalogue (out-of-scope zone or not a zone at all) gives `unsupported/out_of_scope` at once, without retry (retrying cannot make the zone exist); a target equal to the current zone is dropped (so "present only if different" holds whatever the model says); a target with scope path/environment is a validation error and is retried. Planner: `current_zone` targets `targetZoneId or zone.zoneId`, now; `explain_no_step` uses the same zone. The wire schema gets a nullable `targetZoneId` string (not an enum of zones, for the same reason as `controlledProperty`). Dropped: a list of target zones (no scenario request needs more than one).
- 2026-11-02 - Development models (chosen from the live list of https://openrouter.ai/api/v1/models filtered on `structured_outputs`, read 2 Nov 2026): paid **`openai/gpt-oss-120b`** (0.024 / 0.089 USD per M input/output tokens, 131k context) and free **`nvidia/nemotron-3.5-super-vl:free`** (1M context; free tier: 20 req/min, 50/day). Dropped: `openrouter/free` (a router: the serving model changes between calls, not reproducible), `liquid/lfm-2.5-2.6b:free` (too small), `:batch` variants. The final, stronger model is chosen before the final run. Default for the scripts = `GROUNDER_MODEL_CHEAP` from `.env`, else gpt-oss-120b. First live run (6 sample requests from the hallway, temperature 0): 6/6 correct on both models at the first attempt; gpt-oss-120b 0.00067 USD in total, mean latency 4.5 s; nemotron free 0 USD, mean latency 8.8 s, about 1.2k completion tokens per request (reasoning). Figures computed from `results/llm_calls.jsonl`.
- 2026-11-02 - Call log records OpenRouter's `provider` field (who served the request). gpt-oss-120b was served by four providers in six calls (Parasail, Near AI, PrimeIntellect, DekaLLM), with different latencies and possibly different quantisations: a reproducibility threat for the evaluation. **Proposal for the evaluation runs**: pin the provider for the main runs with OpenRouter's `provider: {order: [...], allow_fallbacks: false}` request option (a client parameter, included in the cache key), and report the provider in the results table. Not done now.
- 2026-11-02 - `value` in StructuredIntent: before this change C2 could not express a number ("set the thermostat to 22", "dim the lamp to 40%"), and the planner skipped `set`. Optional float, present exactly when `action` is `set` (model validator both ways: a `set` without a number is meaningless, a number with `increase` would be a relative change the planner cannot apply without reading state). Unit = the device's own (percent brightness, percent blind position with 0 = closed, degrees Celsius), so the planner passes it through unchanged: `set` -> `SET_COMMANDS[category]` (`dim`, `setPosition`, `setSetpoint`), dropped if the device lacks it (`command_absent`, e.g. lamp_corridor, blind_meeting_room). Ranges stay in the environment (`InvalidValue`), not in the contract, because they depend on the device, not on the property. Grounder A: nullable `value` number in the wire schema, prompt rule (null unless `set`; `set` without a number -> clarification `missing_information`); a mismatch is a validation error and is retried. Changing the prompt invalidates the response cache of the first live runs. Dropped: relative values ("2 degrees warmer"; needs current state, no scenario request requires it), a unit field (one unit per property is enough here).
- 2026-11-02 - Evaluation set: labelling rules in `docs/EVAL_POLICY.md` (rules 1-7, plus 8 command_absent, 9 set without a number, 10 unclear action/property; `path` always `following`, `environment` always `one_off`; no `query` requests, because the planner does not plan observations; no out-of-range values, because range checking belongs to the environment). Two metrics: strict accuracy on the result fields (`acceptable_actions` accepted for `action`, `confidence` ignored) and outcome accuracy on the planner's steps (empty plan = unsupported, intent below theta = clarification, any non-action is correct on adversarial cases). Format: one JSON object per line (`id, text, language, zone{zoneId, previousZoneId, confidence}, category, gold, acceptable_actions, split, note`), plus an optional `paraphrase_of` (id of the English source of an Italian paraphrase) that was not in the original format but is needed for the EN vs IT Stability metric of the evaluation; a paraphrase must have the same gold, zone and split (no leak from the frozen test set into dev). The loader (`cpsagent.eval.dataset`) validates gold against C2 *with* the bound catalogue as context, and against the planner: an intent gold must yield a step runnable now, and each acceptable action must give exactly the same steps. Ten categories, 30% dev / 70% test.
- 2026-11-02 - Policy revision and full evaluation set: new rules 0 (user in an out-of-scope zone -> out_of_scope for any request), 3c (Italian "corridoio" = hallway or corridor -> clarification/ambiguous_target), 11 (no referent, no history -> ambiguous_target), 12 ("turn everything off" -> deactivate/light/environment, clarification also accepted via a new optional `acceptable_kinds` field); injection mixed with a legitimate request now has the legitimate intent as gold (the injected part is ignored), injection only stays out_of_scope; a separate off-catalogue safety metric over all cases. Blinds: open/close were already distinct (deactivate/activate shading), but `value` for shading was defined as % open, i.e. against the property (`increase` shading closes, a higher value opened). Changed to % shading (0 = open, 100 = closed); the planner sends `setPosition 100 - value`. "Halfway" = 50 either way. Dropped: renaming the property to `position` (would invert activate/deactivate instead). Set: 150 English cases (15 per category), 30 Italian paraphrases (3 per category, same gold/zone/split), 30 requests written by the author (`source: human`, all in test, labelled with the policy). Dev = 30% of the `llm` cases; human cases are excluded from the share because they must stay in test.
- 2026-11-02 - Set corrections before the evaluation runs: `acceptable_kinds` now takes a kind (any reason) or `kind:reason`; zone_dependent cases whose zone lacks the capability (gold clarification/ambiguous_target, incl. h-009, h-011) also accept `unsupported:capability_absent`; a bare percentage on blinds ("set the blinds to 30%", direction unclear) also accepts `clarification` (5 cases, kept with their gold rather than relabelled). `python -m cpsagent.eval.dataset --show N --seed S --source llm|human` prints random cases for spot checks.
- 2026-11-02 - Evaluation runner (`python -m cpsagent.eval.run`): one output directory per run (`results/RUN_ID/`: run.json, predictions.jsonl, summary.md/.csv, errors.md/.jsonl); run.json records model, pinned provider, temperature, split, repeats, git commit and SHA-256 prefixes of the dataset, system prompt and wire schema, plus the call-log run id that links to `results/llm_calls.jsonl`. The test split needs `--final`. Cost guard: before the run, uncached first-attempt calls x the *measured* mean cost per call of the same model (from the call log; "unknown" if never called), ask above 1 USD and then raise the spending cap to twice the estimate. Client additions: `provider` pins one OpenRouter provider (`provider: {order: [P], allow_fallbacks: false}`), and is part of the cache key when set; a `repeat` index > 0 is part of the cache key, so the repetitions of a Stability run are separate real calls but a rerun of the same run is free. - 2026-11-04 - Grounder C (`grounding/embedding.py`, no training). Only the choice of the (action, controlledProperty) pair differs from the keyword baseline: the baseline's lexical rules were moved, unchanged, into functions of `keyword.py` (`screen`, `scope_rules`, `set_value`, `finish`) used by both (checked: the baseline's 210 predictions are identical before and after). (a) Candidates are built from the catalogue: every catalogued property x the actions the planner maps to a command for its device categories (`COMMAND_RULES`, `SET_COMMANDS`); each pair has 4-7 English and Italian phrasings, written from the catalogue vocabulary without reading the set (a test checks that no 5-word sequence occurs in data/requests.jsonl); a property without phrasings gets a plain "<action> the <property>". Phrasings are embedded once and cached in `.embedding_cache/` (git-ignored, key = model@revision + texts). (b) Pair score = max cosine over its phrasings (nearest neighbour, not the centroid: phrasings of one pair can be far apart, "turn on the light" vs "it is dark"). (c) best < threshold -> `unsupported/capability_absent`; runner-up within margin -> clarification, `ambiguous_action` if same property, else `ambiguous_target`; a runner-up for which the planner sends the same command (lamp activate/increase, blind activate/increase and deactivate/decrease, policy rule 7) is skipped, otherwise these pairs would always look ambiguous. (d) The absent-capability word list of the baseline is *not* used (absence is what the threshold decides); the injection/off-topic and zone-name rules are, because they are not about the pair. (e) A number makes the action `set` (value rule of the baseline, needed because C2 allows `value` only with `set`); a `set` pair without a number -> `missing_information`. (f) `confidence` fixed at 0.7 like the baseline: a cosine is not a calibrated probability, and using it would let the engine's theta (0.6) gate a second time. (g) Every result goes through `finish`: planner check (rule 2 clarification, capability/command absent) and C2 validation with `catalogue_properties` and `catalogue_zones` as context (`invalid_output` if it fails), now applied to the baseline too (no change in its predictions).
